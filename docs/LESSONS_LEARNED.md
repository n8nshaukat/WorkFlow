### LL-001: `npm install` Fails Reliably Inside This Project's Google-Drive-Synced Folder
`[Environment / Google Drive]`
Confirmed twice, reproducibly, right at scaffolding time: `npm install` run directly inside `H:\My Drive\Claude Projects\WorkFlow\` fails with `EPERM: operation not permitted, rmdir ...` during npm's own cleanup pass, followed by `EBADF: bad file descriptor`, leaving a near-empty `node_modules` (no `.bin`, nothing usable). The exact same `package.json` installed cleanly (87 packages, clean build) copied to a plain local temp folder outside Drive sync. This is the same class of issue the sibling SAL Operations project has documented and partially worked around (Drive's virtual filesystem adds real per-file I/O overhead and, for npm specifically, breaks its rename/rmdir dance during a large multi-file install like `node_modules`) — but here it's an outright failure, not just slowness.
**Why:** Google Drive's local sync client intercepts file operations on a virtual filesystem layer; npm's install process does rapid create/rename/delete cycles across thousands of small files (`node_modules`), which Drive's sync layer doesn't handle as a plain local disk would.
**How to apply:** Never run `npm install` (or anything that writes a large `node_modules`) directly inside this repo's Drive-synced path. `node_modules` is gitignored anyway, so nothing is lost by keeping it out of Drive entirely — either work from a plain local git clone (recommended; matches what SAL Operations' own unresolved "Someday" item already recommends doing for itself), or, if working directly in the Drive folder is preferred for some other reason, install into a local path and symlink `node_modules` back in. `git` operations (status/add/commit/push) on the source files themselves are unaffected — only npm's own install-time file churn triggers this.

### LL-002: A Loose `^` Version Range on `eslint-plugin-react-hooks` Resolved to an Incompatible Config Shape
`[Tooling / ESLint]`
Scaffolded `eslint.config.js` by copying the sibling SAL Operations dashboard's working pattern (`reactHooks.configs.flat.recommended`), but wrote `"eslint-plugin-react-hooks": "^5.0.0"` in `package.json` from memory instead of checking what version the sibling project actually has installed (`^7.1.1`). npm resolved `^5.0.0` to `5.2.0` — a real published version, but one whose `configs` export dropped the `flat` namespace entirely (it exposes `recommended`, `recommended-legacy`, `recommended-latest` instead), so the copied config line crashed with `Cannot read properties of undefined (reading 'recommended')`. Fixed by pinning the same major version range the sibling project actually uses (`^7.1.1`), not by chasing the newer API shape — confirmed the original `flat.recommended` line is correct once the version matches.
**Why:** A config snippet copied from a working sibling project is only actually valid for the *version* of that dependency the sibling project has installed — the same import path (`configs.flat.recommended`) is a real, working API in one major version and a `TypeError` in another. Guessing a version range "from memory" instead of checking the sibling's `package.json` directly is exactly how this mismatch happened.
**How to apply:** When copying a config pattern (ESLint, Babel, bundler config, etc.) from another project in this same account, copy its dependency *versions* too, not just the config file's contents — grep the sibling project's `package.json` for the exact range in use rather than writing a plausible-looking one from memory. If a copied config throws on a method/property that "should" exist, suspect a version mismatch before assuming the copied code is wrong.

### LL-003: A Sibling Project's "Critical Rule" Was Carried Into CLAUDE.md Without Re-Confirming It Against This Project's Own Requirements
`[Process / Requirements]`
CLAUDE.md's original "Critical Rules" section stated "click-to-edit, not drag-to-resize" as a rule to apply "from day one," inherited wholesale from SAL Operations' own CLAUDE.md. It got applied to the first interactive mockup (no drag interaction at all) before the user had ever actually weighed in on it for WorkFlow specifically. When the user later asked for drag-to-resize and drag-to-link-dependencies, they said explicitly they hadn't ruled drag out and didn't know where that restriction came from — because they hadn't stated it; it arrived through carried-forward scaffolding, not through a decision made for this project.
**Why:** A rule inherited from a sibling project's real, hard-won lesson is still just an assumption until it's confirmed against *this* project's actual requirements — even when it's labeled "critical" and even when the underlying engineering rationale (ambiguous intent on a drag, silent-wrong-edit risk) is sound in the abstract.
**How to apply:** When a "carried forward" rule from another project in this account is about to shape a concrete deliverable (not just inform it), surface it to the user explicitly before building against it, rather than silently treating it as settled. If the user overrides it, update CLAUDE.md in the same session rather than leaving the doc and the actual product decision out of sync.

### LL-004: A Correct Fix Can Still Be the Wrong Diagnosis — Chase the Root Cause, Not the First Plausible Bug
`[Frontend / CSS / Debugging]`
The interactive mockup's Gantt/Network/Guide panes reportedly could not scroll, in either direction. First diagnosis: the scroll containers (`.board-scroll`, `.net-scroll`, `.guide-scroll`) were missing `min-height:0`, a real, well-known flexbox trap (a `flex:1` item's default minimum height is "as tall as its content," so it grows to fit everything instead of clipping and scrolling). That fix was applied, published, and **did not resolve the bug** — the user reported it was still broken, plus a new, unrelated symptom (a dead vertical scrollbar sitting on the tab bar, caused by a *different* earlier fix: `overflow-x:auto` implicitly sets `overflow-y:auto` too per the CSS spec when only one axis is declared). Re-diagnosing from scratch rather than assuming the first fix "mostly" worked led to the actual root cause: `body{height:100%}` was set, but `html{height:100%}` was not — and this project's own loaded `artifact-design` skill guidance *explicitly* says a one-screen app needs `height:100%` on **both** `html` and `body`, specifically instead of `100vh`, so that the platform's safe-area padding on `:root` is respected. Without a definite height on `html`, `body{height:100%}` resolves to `auto`, and the entire flex chain below it — including the correct `min-height:0` fixes — has nothing to actually shrink against. The `min-height:0` fix was real and necessary, but not sufficient, and reported as fixed before it was verified against the actual complaint.
**Why:** A plausible, textbook-correct CSS fix (min-height:0 is a genuinely common flexbox bug) can coexist with a deeper, unrelated root cause. Publishing a fix and reporting "fixed" without being able to visually verify it in a real browser meant the failure only surfaced through another round of user feedback — twice. The second, correct diagnosis was sitting in already-loaded skill instructions from earlier in the very same session, not something that needed rediscovering.
**How to apply:** When a fix doesn't resolve a reported bug on retry, don't reach for the next plausible CSS hypothesis in isolation — re-check it against any platform/skill guidance already loaded in the session first (it may directly specify the exact setup required, as `artifact-design` did here for `html`+`body` height). When a fix can't be visually verified before reporting it back, say so plainly rather than implying confidence the tooling can't back up.

### LL-005: `FileReader.readAsBinaryString` Is Non-Standard — Use `readAsArrayBuffer` for SheetJS/XLSX Parsing
`[Frontend / Import / Browser APIs]`
The Excel/CSV importer (built on the SheetJS `xlsx` library) read the uploaded file with `reader.readAsBinaryString(file)` and `XLSX.read(reader.result, {type:'binary'})` — a pattern copied from older SheetJS examples. The user reported the Excel import simply wasn't recognized. `readAsBinaryString` was never part of the FileReader spec (it was a legacy Firefox/Mozilla extension method); modern browser support for it is inconsistent, unlike the standard `readAsArrayBuffer`. Switched to `reader.readAsArrayBuffer(file)` with `XLSX.read(new Uint8Array(reader.result), {type:'array'})`, the pattern SheetJS's own current docs recommend.
**Why:** Copying a working-looking code snippet (including from an authoritative library's own older examples) doesn't guarantee the API it calls is still broadly supported — non-standard/legacy browser methods are an easy thing to carry forward unnoticed.
**How to apply:** For file-reading code via `FileReader`, prefer `readAsArrayBuffer` (standard, universally supported) over `readAsBinaryString`/`readAsDataURL` unless a library specifically requires one of those. When wiring up a third-party parsing library, check its *current* docs for the recommended input type, not just whichever snippet is easiest to find.

### LL-006: An "Ask Claude to Interpret" Import Path Silently Truncated Large Real Documents — Assumed the Wrong Failure Mode Entirely
`[Frontend / Import / AI-assisted parsing]`
The PDF-import feature was designed around a worry raised without a real document to test against: that the user's source PDFs might be scanned/image-only (no selectable text). When the user finally shared a real source document — a 405-row, 7-page MS Project schedule export with fully clean, selectable tabular text — that worry turned out to be wrong. The actual problems were different: the pasted text would be large (way past the `text.slice(0,6000)` hard-coded into the `sample.json()` prompt call, silently dropping ~78% of a document this size with no warning to the user), duplicate-heavy (Gantt bar labels repeat every task name, plus headers/footers repeat once per PDF page), and hierarchical (WBS parent/rollup rows summarize their own children's date spans — importing every row flat as a task would double-count the same calendar range at multiple levels). None of this was discoverable from the code or from reasoning about the feature in the abstract; it only became visible once a real, representative document was in hand.
**Why:** A plausible-sounding worry about *why* a feature might fail (scanned/OCR) can be completely wrong and still block progress if never checked against a real example. Generic AI-interpret paths built for "some messy text" have hidden ceilings (token/character slices, no structure-awareness) that only show up at real-world scale, not in small hand-written test cases.
**How to apply:** Before building or fixing an import/parsing feature meant for real user documents, get an actual representative sample as early as possible — don't design around a hypothesis about what the data looks like. When a pasted/uploaded document is sent through an LLM-interpret path with any kind of length limit (a slice, a token cap), either raise it to cover realistic document sizes, chunk-and-merge across calls, or tell the user plainly that it was truncated — never truncate silently. When the source data has real structure (a table, a hierarchy, consistent columns), prefer a deterministic parser over an AI-interpret call: it has no size ceiling, no ambiguity risk, and is easy to verify with a plain unit test (see `scratchpad/test_wbs_parse.js` from the session that found this, not committed to the repo).

### LL-007: After Two Static-Analysis Fix Attempts Fail, Stop Guessing and Add Diagnostics — Don't Try a Third Plausible Fix Blind
`[Process / Debugging]`
A drag-to-link-dependency feature was reported broken across six consecutive rounds of live user testing. The first two fix attempts were each individually reasonable — more robust drop-target hit-testing (bounding-box scan instead of a single-pixel `elementFromPoint` sample), then full toast feedback on every code branch so a silent no-op couldn't masquerade as "nothing happened" — but neither was the actual bug, and the feature stayed broken. A third attempt (round 7) found a real, confirmed root cause via careful re-reading of the CSS (`.bar{overflow:hidden}` was clipping the very hit-area the round-3 fix had added) and fixed it — but the feature *still* didn't work after that fix shipped. Only after adding actual `console.log` instrumentation and a `try/catch` around the failure path, and asking the user to paste back real browser-console output, did the true bug surface: a `TypeError` from mutating a frozen array (see LL-008), several rounds removed from any of the CSS/DOM hypotheses chased so far.
**Why:** Static code review from outside a browser cannot see runtime state (frozen objects, actual computed styles, real event timing) — every fix up to round 7 was a genuinely reasonable hypothesis given what was visible in the source, and every one of them was wrong. Continuing to generate plausible-sounding fixes without new evidence is not debugging, it's guessing with extra steps, and it burns the user's patience for each round that "should have fixed it" but didn't.
**How to apply:** If a live-tested bug survives two rounds of confident static-analysis fixes, the next move is not a third guess — it's adding real diagnostics (console logging at each step, a try/catch that surfaces exceptions instead of swallowing them) and asking the user to run it with DevTools open and paste back the actual output. Say this explicitly rather than attempting a fourth blind fix: static review has a real ceiling, and hitting it is a normal, expected point to escalate to runtime evidence, not a failure to reason harder.

### LL-008: A Platform Capability's "Frozen Snapshot" Data Survived a Shallow Object Spread, Crashing Every In-Place Array Mutation Downstream
`[Frontend / Data Layer / Platform capabilities]`
Tasks loaded from the Claude Artifact's bundled `db` capability (`deserializeTasks`, called on every project load) were deserialized with `{...t, start:D(t.start), end:D(t.end)}` — a shallow object spread. This produces a genuinely fresh, mutable *top-level* task object, which masked the real problem: the capability's own `snap.data()` appears to return a non-extensible (frozen) snapshot, and a shallow spread copies nested properties (`history`, `preds`, `resources`) *by reference*, not by value — so those nested arrays stayed frozen forever, invisibly, inside an object that looked completely normal. Any code that mutated one of those arrays in place (`array.push(...)`, `array.unshift(...)`) threw `TypeError: Cannot add property N, object is not extensible` — but only sometimes, since code paths that *reassigned* the property instead (`it.preds = newArray.slice()`) worked fine, making the bug look intermittent/path-dependent rather than structural. Confirmed via a live browser stack trace (see LL-007) after two other hypotheses were chased first.
**Why:** `{...obj}` (or `Object.assign({}, obj)`) is a shallow clone — it creates a new outer object but every nested object/array is still the *same reference* as the source. Freezing/sealing is invisible in a debugger's casual inspection (the object prints normally) and only surfaces the moment something tries to mutate it in place, which can be arbitrarily far downstream from where the frozen data was actually read. A capability boundary (a platform API returning cached/read-only data) is exactly where this kind of defensive immutability is most likely to appear, expected or not.
**How to apply:** When deserializing data that crossed any kind of read boundary you don't control (a platform capability, an external API, `JSON.parse` of something you didn't just `JSON.stringify` yourself) and you intend to mutate it later, explicitly clone every nested array/object you'll touch — a shallow spread is not enough once mutation is in-place rather than reassignment. Prefer reassignment over in-place mutation as a general habit for exactly this reason (`arr = [...arr, x]` instead of `arr.push(x)`, `arr = [x, ...arr]` instead of `arr.unshift(x)`) — it's immune to this entire class of bug regardless of where the array came from, and was applied as a belt-and-suspenders fix alongside the real clone-at-the-boundary fix.

### LL-009: An Enlarged Click-Target Fix Was Silently Negated by the Parent's `overflow:hidden` — and Nested `position:sticky` Silently Failed to Stick a Descendant
`[Frontend / CSS]`
Two separate bugs, same shape: a CSS technique was applied correctly in isolation but silently defeated by an ancestor's own, legitimate CSS property. (1) A drag-handle "knob" was enlarged via an invisible `::before` pseudo-element extending beyond its own box, to make it easier to grab — but the knob was a *child* of `.bar`, which has `overflow:hidden` (needed elsewhere, to clip the progress-fill to the bar's rounded corners). Anything positioned outside `.bar`'s own box — including the entire enlarged hit-area — was silently clipped away, making that whole fix a no-op for weeks of the session's testing without any visible error or warning. (2) Two rows needed to stay visible while scrolling both vertically (pinned below the date header) and horizontally (their label pinned to the left) — implemented as `position:sticky` on the row (vertical) with its child `.row-label` *also* independently `position:sticky` (horizontal). Nested sticky positioning is a known cross-browser trouble spot; the child's horizontal stickiness silently failed to apply while nested inside an already-sticky parent.
**Why:** Both bugs share a root cause: a CSS technique that depends on an element's positioning/sizing extending beyond expectations (a hit-area bigger than its visible box, a sticky child inside a sticky parent) can be silently negated by an ancestor's own property, with no console error, no visual glitch obviously pointing at the cause — the element just doesn't behave as coded, and the natural next step (double-checking the technique itself) doesn't find anything wrong, because the technique *is* correct in isolation.
**How to apply:** When a CSS positioning/sizing technique isn't working as expected, check every ancestor's `overflow`, `position`, and other containment-affecting properties before re-deriving the technique itself — the bug is often two levels up, not in the code you're staring at. Avoid nesting `position:sticky` across a parent and child on different axes; apply both sticky axes to leaf elements directly (or to the same element) with no sticky ancestor in between, since nested sticky-in-sticky is unreliable across browsers. For enlarged hit-areas via pseudo-elements or negative-offset positioning, prefer moving the element to be a sibling (not a descendant) of anything with `overflow:hidden`, rather than assuming the enlargement will simply render outside the clip.

### LL-010: A Real Apostrophe Inside a Single-Quoted JS String Literal Broke the Guide Tab Silently (No Runtime Error Until Page Load)
`[Frontend / JS syntax]`
Editing the Guide tab's copy (plain prose, written straight into `'...'`-quoted arguments inside a template literal) introduced three separate instances of an unescaped apostrophe — `'there's something to assign'`, `'summary's bar'`, `'group's overall'` — each of which silently closed the string early and turned the rest of the line into invalid JS. This was never caught by eye across two separate edits (guide copy, then the grouping-feature copy added right after it) because the text reads perfectly normally and the break is purely lexical, not visual. It was only caught by running `node --check` against the file before publishing — without that step this would have shipped as a page that fails to load at all (a `SyntaxError` breaks the entire script, not just the Guide tab), caught only whenever someone next opened the live mockup.
**Why:** `'...'` and `"..."` are equally "just quotes" to write prose into, but a contraction's apostrophe is indistinguishable from the closing quote to the parser — there's no way to catch this by re-reading the sentence, since the sentence still looks completely correct as English.
**How to apply:** Never write user-facing prose containing a plain apostrophe/contraction directly inside a single-quoted JS string; either use a curly apostrophe (’) in the copy — which reads identically to the user and can't collide with `'` — or double-quote the string instead (safe only until the copy needs a real double-quote). Whichever is chosen, run `node --check` (or equivalent) on any hand-edited `.js` file before publishing it — this is a near-zero-cost step that would have caught this immediately, and should be routine after any edit that touches a template-literal string, not just this one.

### LL-011: An Early `return` Inside `loadState()` Skipped Its Own Safety-Net Check, Leaving `project()` Able to Return `undefined`
`[Frontend / JS control flow]`
User reported PDF import as "broken" — parsing appeared to succeed (status text updated) but the review/edit table never appeared. Two rounds of reading `parseWbsTable`/`renderReviewTable` by eye found nothing (per LL-004/LL-007's own lesson, this alone should have been the signal to stop and ask for a real trace sooner). The user's browser console gave the real answer immediately: `Cannot read properties of undefined (reading 'tasks')` inside `leafTasks`, called from `renderPobBanner`, called from `renderAll`. `project()` (`PROJECTS.find(p=>p.id===state.projectId)`) had returned `undefined`. `loadState()` does have a safety-net line at its very end — `if(!PROJECTS.find(p=>p.id===state.projectId)) state.projectId=PROJECTS[0].id;` — meant to catch exactly this. But the `if(!DB){ ...; return; }` branch near the top of the function (taken when the `db` capability is unavailable) `return`ed early, skipping that check entirely. The bug wasn't in the code that crashed — it was in an unrelated early exit several lines above, in a completely different branch.
**Why:** A safety-net check placed at the end of a function only protects code paths that actually reach the end. An early `return` (or `throw`, or any other early exit) added to ONE branch of that function — often long after the safety net was written, for an unrelated reason — silently opts that branch out, with nothing at the call site or the check itself indicating the gap exists.
**How to apply:** When a function ends with a general-purpose invariant check ("make sure X is always true before this function hands control back"), audit every early exit inside that function to confirm each one still reaches the check — restructure with `if/else` rather than early `return` when a shared closing step must never be skippable. This is also the second time this project's own debugging pattern paid off exactly as documented: don't keep guessing from static reading after the first attempt turns up nothing — ask for the actual console trace, then fix precisely what it points at instead of the nearby code that merely looked suspicious.
